# Local Research Interface

The optional Streamlit interface is a **functional local research workbench**, not a trading engine. It starts in an explicit fixture-data mode so users can exercise the complete local workflow before a later approved broker-data sync stores a validated instrument master and research datasets.

Run it only after installing the optional local UI dependency:

```bash
python -m pip install -e ".[local-ui]"
python -m streamlit run src/algo_manus/ui/app.py
```

Fixture mode lets a user select one or more labelled local sample securities, tune an SMA parameter revision, run the real local experiment/backtest application service, inspect per-security KPI/trade/equity output, sort the multi-security leaderboard and simulate the deterministic paper-risk/event lifecycle. Fixture results are never broker data, real market evidence or a performance claim.

## Public Angel One instrument master (Option A)

The **Data & instruments** page provides one explicit **Download public Angel master** action. It retrieves only Angel One’s credential-free public ScripMaster JSON and stores the normalized result as an immutable SQLite snapshot at `~/.algo-manus/instrument_master.sqlite3` by default. Set `ALGO_MANUS_DATA_DIR` before starting the interface to choose another local directory. The source action is manual only: opening the page, importing the application, checking status and reading a preview never download or refresh the source in the background.

The retained snapshot preserves the public source URI, retrieval time, SHA-256 content identity, canonical broker/exchange/segment/token identity and typed instrument metadata. An unchanged public file is deduplicated by content hash while its manual check time is recorded; a changed public file produces a new immutable snapshot. The visible status and bounded preview are read-only evidence. The existing fixture research universe remains explicitly separate until a later, separately approved historical-data workflow persists validated datasets and wires an approved universe.

Option A does **not** authenticate to Angel One, request API keys, create a session, access profile/account/funds/holdings/positions, retrieve prices or historical candles, connect a WebSocket, submit/cancel paper or live orders, schedule a refresh, or enable cloud execution. A transient public-source failure or malformed record leaves the prior local snapshot unchanged and visible; the interface does not substitute fixture data or silently use an alternative provider.

## Authenticated Angel One historical candles (Option B)

The same **Data & instruments** page now provides a separate **Download research candles** action. It is manual only and is available only after a retained Angel public-master snapshot identifies the selected canonical `ANGEL_ONE` instrument. It calls the documented historical-candle endpoint through the existing typed market-data port, validates the requested interval and maximum documented request span before transport, normalizes closed OHLCV bars, and persists each successful response as an immutable source-aware dataset in `~/.algo-manus/market_data.sqlite3` by default. The local status and bounded preview read existing evidence only; importing, rendering, checking status and previewing data never contact the broker.

Option B accepts a transient access token from the local session boundary, while retaining only the SmartAPI app key and MAC-address header value as long-lived local configuration. A legacy existing-token handoff is optional, but it is not persisted. A missing active session or incomplete local header configuration disables the manual action before any historical-data network call. A provider error, malformed envelope/candle, unsupported instrument/interval, or request beyond the documented maximum span fails closed and does not create a dataset.

This Option B path is **research-only**. It does not replace the fixture universe or fixture experiments, establish data quality, calculate performance, fetch live prices, access profile/account/funds/holdings/positions, use a WebSocket, schedule refreshes, submit/cancel paper or live orders, or enable execution. The separately bounded local session lifecycle is described in Option C below; it adds no other broker capability.

## Local Angel One session handling (Option C)

Option C adds a separate, manual local session lifecycle for the already-approved historical-candle adapter. The Data & instruments panel displays only a configuration/active-in-memory state and acquisition time; it has no text fields for credentials or tokens. A locally configured user can explicitly choose **Start local session**, **Refresh local session** or **Forget local session**. Start and refresh use only the documented Angel login and token-generation endpoints. Forget clears the in-memory token handoff and makes **no** remote logout request.

The ignored `.env.example` documents the local names `ALGO_MANUS_ANGEL_APP_KEY`, `ALGO_MANUS_ANGEL_MAC_ADDRESS`, `ALGO_MANUS_ANGEL_CLIENT_CODE`, `ALGO_MANUS_ANGEL_PIN`, `ALGO_MANUS_ANGEL_TOTP`, `ALGO_MANUS_ANGEL_LOCAL_IP` and `ALGO_MANUS_ANGEL_PUBLIC_IP`. The TOTP value is an already displayed authenticator code, not a stored seed and not a code generated by the application. All credential values and the returned JWT, refresh and feed tokens are excluded from representations, UI, logs, exception details, SQLite, files and version control. Tokens live only in process memory and are handed only to the research-only historical adapter.

Option C still does **not** access profile, account, funds, RMS, holdings, positions, market prices, feeds, WebSockets or any order/cancellation endpoint. It does not schedule login, refresh, retries or logout, and it does not enable paper execution or live execution. Token/session expiry remains provider-controlled: the user must explicitly refresh or start a new local session after a provider failure. No other broker capability is implied by local session readiness.

## Retained broker dataset research backtests (Option D)

Option D adds a separate **Retained Angel historical-dataset backtest** panel under Backtesting. It lists only bounded, already retained local datasets whose source is `angel_one`; it does not download, refresh or otherwise request broker data. The user explicitly selects one dataset identity, chooses one registered research strategy and execution assumptions, and manually starts a single-security research backtest. The fixture backtest controls, fixture history and fixture labels remain unchanged and visibly separate.

Before a retained dataset can be backtested, the application requires its provenance to identify an Angel One broker source and research use, checks that retrieval did not predate the final retained bar, and evaluates the existing local research dataset policy. Missing, rejected or quarantined datasets fail closed without creating an experiment batch. A successful run persists an immutable experiment batch and research manifest that pin the dataset ID, canonical instrument ID, interval, source URI, retrieval timestamp, raw-content SHA-256, adjustment basis, accepted validation outcome, strategy revision and execution assumptions. The evidence record’s information cutoff is the final retained candle timestamp.

The backtest engine remains next-bar conservative: a signal derived using candles through time *t* can only fill at the open of candle *t + 1*. This is an execution-timing control, not a claim that the retained broker dataset is complete, adjusted for corporate actions, error-free or suitable for any strategy. The application does not silently use fixtures when an Angel dataset is unavailable, and it does not turn a retained-data result into market validation, a performance claim, paper evidence or trading advice.

Option D adds no new broker endpoint or session capability. It still excludes account/profile/funds/RMS/holdings/positions, live prices, WebSockets, background refresh, scheduler, paper price fetches, paper orders and live execution.

The **Risk & paper** page now initializes and reads a local SQLite control store under `~/.algo-manus/risk_controls.sqlite3` by default. Set `ALGO_MANUS_DATA_DIR` before starting Streamlit to choose another local directory. The page shows the active local central-policy version, durable kill-switch state, append-only control-change history and the latest central decision evidence. Persisting a kill-switch change updates only that local control record; it does not contact a broker or cancel any external order because no external order path exists.

The fixture paper simulator uses local sample marks and a durable local event ledger. The **Risk & paper** page replays that ledger against an explicit ₹100,000 fixture starting cash to show local cash, long-only positions, realised P&L and order state. Its event record carries persisted policy/kill-state identity when a fixture proposal is evaluated, but it is not a broker-confirmed order, paper-market fill or reconciliation result. See `docs/LOCAL_PAPER_PROJECTION.md` for replay assumptions and limitations.

## Canonical local paper event spine (Option E)

The local ledger now retains one canonical simulated lifecycle: proposal, deterministic risk decision, local acceptance or rejection, optional working state, partial or final simulated fills, cancellation and non-destructive reconciliation evidence. A new accepted local lifecycle must have retained allowed-risk evidence before its acceptance event. Paper cash, long-only positions, realised P&L, order fill totals and remaining quantity are replayed from retained fill evidence only; proposal, risk, acceptance, cancellation and reconciliation records do not alter those values by themselves. Duplicate, excessive, malformed, missing-risk or out-of-sequence events remain retained and are reported as unprojectable rather than repaired or financially applied.

The **Risk & paper** page exposes read-only event-derived positions, projected P&L, cumulative filled quantity, remaining quantity, reconciliation disposition and canonical lifecycle filters through application read services. A reconciliation record is only a local comparison disposition with a reason; it does not contact a broker, compare against broker data, mutate a prior event, apply a correction, or prove external reconciliation. The workbench still has no broker account/holdings/positions/funds/order-history access, live price source, paper broker, WebSocket, scheduler, autonomous fill path or live execution capability. See `docs/LOCAL_PAPER_EVENT_SPINE.md` for the exact event rules and exclusions.

## Conservative local limit-fill simulator (Option F)

The **Risk & paper** simulator now accepts explicit local assumptions for a `LIMIT` price, caller-supplied observed price, caller-supplied available quantity, adverse slippage, and a local session-open flag. A non-limit assumption is rejected before a new local event is appended. A closed session, limit-ineligible effective price, or zero declared local availability retains an `ORDER_UNFILLED` no-fill event and leaves replayed cash, positions and realised P&L unchanged. Eligible declared quantity can produce only a volume-capped partial fill or a final fill, with every assumption, decision outcome and reason retained on the local event.

These are **not** broker prices, traded volume, order-book liquidity, queue position, venue fills, broker acknowledgements, or live market data. The audit timeline can display and filter the retained no-fill simulator evidence, along with local limit, observed-price, availability, adverse-slippage and session assumptions. The page remains an application-service-only local simulation interface; it does not add a paper broker, market-data retrieval, WebSocket, background task, scheduling, external reconciliation or live execution. See `docs/LOCAL_LIMIT_FILL_SIMULATOR.md` for exact decision rules and exclusions.

## Local in-process event wiring (Option G)

The local workbench now uses a bounded in-process event bus only after source evidence has been retained. Research batches publish a reference after their manifest and batch save; paper lifecycle events publish a reference after their immutable local paper-ledger append. The **Risk & paper** page exposes a read-only current-process wiring audit containing each event type, correlation, producer, durable source-evidence ID and isolated subscriber delivery/failure count.

The trace is deliberately non-durable and empties on application/process restart; the pre-existing local research and paper SQLite evidence remains authoritative. It contains no network, external queue, Kafka/RabbitMQ/SQS/PubSub service, webhook, worker, scheduler, retry path, cloud service, broker call, price feed, account call, paper broker or live execution. See `docs/LOCAL_EVENT_BUS.md` for dispatch, ordering, duplicate, failure and restart semantics.

It consolidates only existing local evidence: replayed portfolio state; lifecycle counts; the latest interpretable retained deterministic risk decision; retained local simulator outcome counts; reconciliation-disposition counts; audit integrity totals; and bounded current-process wiring diagnostics. Its detailed rows are still available through the existing read-only local audit views.

This console is not an order-management system, broker/dashboard terminal, account/position source, market valuation, venue-status feed, reconciliation proof or live control plane. It cannot submit, fill, cancel, reconcile, publish, subscribe, retry, replay, repair, synchronize, export, call a broker, retrieve a price, open a WebSocket, run a scheduler or route any order. Current-process wiring diagnostics remain non-durable and empty after restart, while local SQLite paper/research evidence remains authoritative. ## Bounded local robustness research gate (Option K)

The **Strategies** page now contains a bounded chronological robustness-gate panel. Its current workbench demonstration uses a fixed four-cell SMA crossover grid, a 50% in-sample partition, one positive embargo bar, and an untouched remaining holdout partition of deterministic fixture candles. The panel records a local SQLite evidence row and shows only the declared candidate rows, in-sample/holdout results, partition boundary, gate state and explicit selection-bias warning. It does not rank or select a candidate.

The underlying local service accepts only a `RESEARCH`-use retained candle dataset, validates all named parameter-grid cells through the registered strategy schema, enforces a 1–64-cell policy cap, and runs each eligible partition separately through the existing next-bar backtester. A signal based on closed bar *t* remains eligible only for the open of bar *t + 1*. Embargo candles are omitted from both partitions. Insufficient partition history is retained explicitly rather than being silently expanded, randomized, substituted, or treated as a pass. The immutable local evidence retains dataset ID, strategy/version, candidate parameter-revision IDs, policy/version/boundaries, costs, quantity, force-close rule, result-spec IDs, warning and recorded time; it is stored in `robustness_evidence.sqlite3` under the configured local data directory.

This is research evidence only. A bounded grid and one chronological holdout do not establish robustness, future performance, suitability, data quality, corporate-action correctness, survivorship control, liquidity realism, or promotion readiness. Robustness evidence does not change the existing immutable research-manifest/validation resolver, paper-promotion rule, deterministic risk gate, or paper-event lifecycle. It adds no broker/account/funds/RMS/holdings/positions capability, live price/feed, WebSocket, data download, order or cancellation endpoint, paper broker, scheduler, worker, external queue, cloud service, autonomous execution, or recommendation. See [`docs/LOCAL_ROBUSTNESS_RESEARCH_GATE.md`](LOCAL_ROBUSTNESS_RESEARCH_GATE.md) for the exact policy and limitations.

## Local paper-run evidence gate (Option L)

The **Risk & paper** page now includes a local paper-run evidence-gate panel. It records an immutable local assessment for one retained experiment/instrument context against the existing persisted promotion resolver, an exact matching robustness record, and the current durable policy/kill-switch snapshot. The retained row names the batch, manifest, robustness evidence, central-policy and kill-switch references, assessment time, and any blockers. A matching robustness record must share the dataset, strategy ID/version, and a candidate parameter-revision ID with the experiment; numerical returns and P&L are never used to make the gate complete.

An `EVIDENCE_COMPLETE` state is strictly informational: it means the listed retained records were present, not insufficient-history, within the fixed local 90-day fixture policy at assessment time, and the durable kill switch was inactive. It is not paper-run approval, a strategy selection, promotion, order permission, risk decision, market-data validation, profitability claim, or recommendation. `BLOCKED` records retain every named reason, including missing or stale research/robustness evidence, a parameter-revision mismatch, insufficient robustness history, and an active durable kill switch. The existing immutable promotion resolver and deterministic proposal-level risk engine continue unchanged and remain independently required by the simulator. See [`docs/LOCAL_PAPER_RUN_EVIDENCE_GATE.md`](LOCAL_PAPER_RUN_EVIDENCE_GATE.md) for exact state and blocker semantics.

## Local corporate-action and calendar review evidence gate (Option M)

The **Data & instruments** page now provides a local corporate-action and calendar review-evidence panel for each retained fixture dataset. It retains two manual declarations—one for corporate actions and one for calendar events—with a full candle-window scope, local reference text, note, review time, declared disposition, immutable dataset/provenance lineage, policy version, assessment time, and all named blockers in local SQLite. Blank references intentionally produce explicit missing-review blockers; unresolved, stale, future-dated, and scope-incomplete declarations remain blocked instead of falling back or being silently treated as reviewed.

`REVIEW_COMPLETE` is strictly informational. It means only that both manual declarations covered the retained candle window and met the local age policy at assessment time. The workbench does not open, download, validate, synchronize, or interpret supplied references; it does not infer events, adjust candles, validate data quality, alter promotion, approve paper activity, evaluate risk, submit an order, or enable execution. It is not proof of corporate-action or calendar completeness, correctness, applicability, adjustment treatment, strategy readiness, market performance, or a recommendation. ## Read-only evidence freshness and lineage coverage (Option O)

It displays one condition row per retained paper-run evidence record, including its linked dataset and instrument identifiers.
