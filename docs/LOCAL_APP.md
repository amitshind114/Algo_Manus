# Local Research Interface

The optional Streamlit interface is a **functional local research workbench**, not a trading engine. It starts in an explicit fixture-data mode so users can exercise the complete local workflow before a later approved broker-data sync stores a validated instrument master and research datasets.

Run it only after installing the optional local UI dependency:

```bash
python -m pip install -e ".[local-ui]"
python -m streamlit run src/algo_manus/ui/app.py
```

Fixture mode lets a user select one or more labelled local sample securities, tune an SMA parameter revision, run the real local experiment/backtest application service, inspect per-security KPI/trade/equity output, sort the multi-security leaderboard and simulate the deterministic paper-risk/event lifecycle. Fixture results are never broker data, real market evidence or a performance claim.

## Public Angel One instrument master (Option A)

The **Data & instruments** page provides one explicit **Download public Angel master** action. It retrieves only Angel One’s credential-free public ScripMaster JSON and stores the normalized result as an immutable SQLite snapshot at `~/.algo-manus/instrument_master.sqlite3` by default. Set `ALGO_MANUS_DATA_DIR` before starting the interface to choose another local directory. The source action is manual only: opening the page, importing the application, checking status and reading a preview never download or refresh the source in the background.

The retained snapshot preserves the public source URI, retrieval time, SHA-256 content identity, canonical broker/exchange/segment/token identity and typed instrument metadata. An unchanged public file is deduplicated by content hash while its manual check time is recorded; a changed public file produces a new immutable snapshot. The visible status and bounded preview are read-only evidence. The existing fixture research universe remains explicitly separate until a later, separately approved historical-data workflow persists validated datasets and wires an approved universe.

Option A does **not** authenticate to Angel One, request API keys, create a session, access profile/account/funds/holdings/positions, retrieve prices or historical candles, connect a WebSocket, submit/cancel paper or live orders, schedule a refresh, or enable cloud execution. A transient public-source failure or malformed record leaves the prior local snapshot unchanged and visible; the interface does not substitute fixture data or silently use an alternative provider.

## Authenticated Angel One historical candles (Option B)

The same **Data & instruments** page now provides a separate **Download research candles** action. It is manual only and is available only after a retained Angel public-master snapshot identifies the selected canonical `ANGEL_ONE` instrument. It calls the documented historical-candle endpoint through the existing typed market-data port, validates the requested interval and maximum documented request span before transport, normalizes closed OHLCV bars, and persists each successful response as an immutable source-aware dataset in `~/.algo-manus/market_data.sqlite3` by default. The local status and bounded preview read existing evidence only; importing, rendering, checking status and previewing data never contact the broker.

Option B uses only a user-managed **existing short-lived access token**, SmartAPI app key and local MAC-address header value from the local environment. The optional `.env.example` documents the names `ALGO_MANUS_ANGEL_APP_KEY`, `ALGO_MANUS_ANGEL_ACCESS_TOKEN` and `ALGO_MANUS_ANGEL_MAC_ADDRESS`, but no actual values belong in version control, the Streamlit interface, test fixtures or chat. The project does not ask for or retain client code, PIN, TOTP, refresh tokens or session information. A missing or incomplete local configuration disables the manual action before any network call. A provider error, malformed envelope/candle, unsupported instrument/interval, or request beyond the documented maximum span fails closed and does not create a dataset.

This Option B path is **research-only**. It does not replace the fixture universe or fixture experiments, establish data quality, calculate performance, fetch live prices, access profile/account/funds/holdings/positions, use a WebSocket, schedule refreshes, submit/cancel paper or live orders, or enable execution. Existing authenticated login, token-refresh and TOTP/session management remain excluded and require separately approved **Option C** security work.

The **Risk & paper** page now initializes and reads a local SQLite control store under `~/.algo-manus/risk_controls.sqlite3` by default. Set `ALGO_MANUS_DATA_DIR` before starting Streamlit to choose another local directory. The page shows the active local central-policy version, durable kill-switch state, append-only control-change history and the latest central decision evidence. Persisting a kill-switch change updates only that local control record; it does not contact a broker or cancel any external order because no external order path exists.

The fixture paper simulator uses local sample marks and a durable local event ledger. The **Risk & paper** page replays that ledger against an explicit ₹100,000 fixture starting cash to show local cash, long-only positions, realised P&L and order state. Its event record carries persisted policy/kill-state identity when a fixture proposal is evaluated, but it is not a broker-confirmed order, paper-market fill or reconciliation result. See `docs/LOCAL_PAPER_PROJECTION.md` for replay assumptions and limitations.

The same page derives a local portfolio-risk snapshot from that replay and explicitly displayed fixture marks. It displays fixture gross/instrument exposure, realised-loss utilisation and the active concentration cap before a local simulation is evaluated. The values are local policy inputs, not market valuation or broker reconciliation. See `docs/LOCAL_PORTFOLIO_RISK.md` for central-limit definitions and the strict local-data boundary.

Before enabling the local fixture-paper button, the workbench now resolves the selected experiment to a persisted immutable research manifest and the exact accepted validation outcome for its selected dataset. The paper decision retains those evidence identifiers. Session-only experiment state from before this promotion gate is blocked until a persisted fixture experiment is run. See `docs/RESEARCH_TO_PAPER_PROMOTION.md` for the evidence chain and limitations.

Fixture experiments are also saved in the local SQLite experiment store and appear in the sidebar count, **Multi-test leaderboard** and **Reporting & analytics** after a Streamlit restart. Those pages allow selecting a persisted batch and show its linked manifest ID before rendering stored KPI summaries. New fixture results also retain bounded local equity-curve and completed-trade artifacts: **Backtesting** reads the selected result’s saved detail and **Reporting** reads the selected batch’s saved trade rows after restart. Older summary-only local batches show an explicit detail-unavailable warning and are never silently recalculated. See `docs/LOCAL_EXPERIMENT_ARTIFACTS.md` for retention defaults and limitations. This is local fixture history only, not a broker-data or performance-record system.

Every newly calculated local backtest also persists a **calculation outcome** alongside its KPI result. The Backtesting result panel, multi-security leaderboard and Reporting view distinguish a calculated result with completed trades from a calculated no-trade outcome, and preserve the available-bar count, next-bar execution history requirement, entry/exit signal counts and completed-trade count. A valid no-trade outcome explicitly states that no eligible SMA crossover occurred or that no complete round trip met the selected execution assumptions; it is not a missing calculation, market claim or recommendation. Existing saved results that predate this field remain readable and are labelled as legacy results with unavailable outcome detail. The local test suite uses explicitly closed test-side SQLite mutation connections so temporary experiment/control databases can be cleaned up on Windows without retaining a `WinError 32` lock.

The **Experiment history** section in **Multi-test leaderboard** now exposes read-only local artifact integrity for every stored batch/result. It reports complete, unavailable, incomplete or result-spec-mismatched detail with expected/actual local row counts, and provides a status filter. The view reads SQLite evidence only; it never repairs records, recomputes fixtures, validates broker data or changes paper-promotion eligibility. See `docs/LOCAL_EXPERIMENT_ARTIFACT_INTEGRITY.md` for the status rules and limits.

The **Reporting & analytics** page also provides a local evidence export for the selected persisted fixture batch. Its summary JSON contains experiment identity, manifest link, stored KPI summaries and artifact-integrity metadata. Detailed equity/trade JSON is offered only when every result is integrity-complete; otherwise the detailed export is refused while the summary remains available. These local files are labelled fixtures and are not broker data, a performance certificate, an execution record or a recommendation. See `docs/LOCAL_EXPERIMENT_EVIDENCE_EXPORT.md` for export contents and refusal rules.

Each available local evidence export now includes a schema/version and deterministic SHA-256 content-verification field. The Reporting export view shows copyable values and canonicalization guidance for offline comparison. This is a local content-check aid only; it is not a signature, trusted timestamp, broker confirmation or tamper-proof audit record.

Downloaded local evidence JSON can be checked without uploading it anywhere by running `python -m algo_manus.application.evidence_verification path/to/export.json`. The command returns an explicit valid, mismatch, missing-verification, unsupported-schema or malformed-payload result and never changes local research records. See `docs/LOCAL_EVIDENCE_VERIFIER.md` for supported schemas and limits.

The **Overview → Local evidence lifecycle** panel shows read-only local store size, retained batch/result/artifact/trade/equity counts, oldest/newest batch times and configured artifact bounds. It deliberately offers no cleanup, deletion, compaction, backup, recovery, cloud synchronization or provider action. See `docs/LOCAL_EVIDENCE_LIFECYCLE.md` for interpretation and limits.

The lifecycle panel also summarizes retained artifact health as complete, unavailable, incomplete or result-spec-mismatched. These statuses are aggregate local SQLite observations only and never trigger repair, regeneration, promotion changes, paper activity or deletion. See `docs/LOCAL_EVIDENCE_HEALTH.md` for their exact interpretation.

The lifecycle panel’s **Health detail filter** exposes read-only batch/instrument identifiers, result-spec IDs, artifact-spec IDs, expected/actual trade and equity counts, creation time and exact status for retained local rows. It defaults to non-complete records and does not repair, export, delete, promote or execute anything. See `docs/LOCAL_EVIDENCE_HEALTH_DETAIL.md` for scope and limits.

The lifecycle panel’s **Chronological local health history** groups current retained artifact-health status counts by batch and displays them oldest-to-newest. It is a present local-state view only; it does not infer what changed, repair evidence, or establish market/strategy history. See `docs/LOCAL_EVIDENCE_HEALTH_HISTORY.md` for interpretation and limits.

The lifecycle panel’s shared **Lifecycle batch scope** and **Inclusive batch creation dates** controls apply the same local read-only scope to health totals, detail rows and chronological history. Dates are inclusive over the selected local calendar days. The controls only filter what is displayed; they do not change retained evidence, integrity status, promotion or paper behavior. See `docs/LOCAL_EVIDENCE_HEALTH_SCOPE.md` for semantics and limits.

The lifecycle panel’s **Compare two local batch health scopes** section compares two distinct retained local batches. It displays local status counts for left and right batches plus the explicit `right − left` count delta. The comparison does not assess performance or market data and cannot change evidence, promotion, paper or execution behavior. See `docs/LOCAL_EVIDENCE_HEALTH_COMPARISON.md` for semantics and limits.

The Risk & paper page’s **Read-only local paper-operation audit timeline** displays retained paper ledger events chronologically with lifecycle state, order/instrument context, retained fixture quantity/price fields, decision context and promotion evidence identifiers when present. Its optional retained-order selector limits only displayed rows and rejects blank/unknown IDs in the application service. It also exposes read-only retained-event totals and per-row integrity status for local payload-shape and lifecycle interpretation; a local scope-preset selector can apply all, valid-only or issues-only integrity scope while leaving the order, event-type, interpreted lifecycle-state, retained payload-side, instrument and UTC time-window controls independent. **Manual integrity filter** exposes the existing integrity selector. Its optional event-type selector narrows the view to a retained local lifecycle event such as risk decision, submission, fill, cancellation, or rejection. Its optional interpreted lifecycle-state selector narrows the view to existing locally derived pending-risk, submitted, filled, cancelled, rejected or unprojectable states without changing the retained sequence or derivation. Its optional payload-side selector narrows the view to already-interpreted retained `BUY` or `SELL` rows. Its optional retained-instrument selector narrows the view to one stored canonical instrument identity. Its optional UTC time-window control applies inclusive retained event-time start/end bounds and rejects inverted ranges. The displayed active-filter summary makes the currently applied local scope explicit without changing it. A row-detail expander can show one selected local event's retained serialized payload and interpreted fields without altering either. These controls never repair or reconcile events. The page cannot submit, cancel, reconcile, amend, synchronize or route any order. See `docs/LOCAL_PAPER_AUDIT_TIMELINE.md` for field meanings and limits.

The local strategy catalog is backed by an explicit in-process registry containing the SMA crossover plus selected high-value research families: EMA crossover, RSI mean reversion, MACD signal, Bollinger breakout and Triple EMA crossover. Each strategy declares versioned metadata, supported instrument types and intervals, a strict parameter schema, risk notes and pure signal behavior. The Backtesting page now selects a registered strategy and renders its validated parameter form; the Strategy manager displays the same catalog. Selected parameters are persisted through the existing experiment application service and appear in the existing leaderboard/reporting evidence. These adaptations still run only on explicitly labelled local fixture data. Strategies cannot receive database, provider, broker, UI or execution access; they may not submit orders directly.

The interface cannot authenticate a broker, create/refresh a broker session, bypass paper risk policy or enable live execution. The approved Option B historical source is a manual research-data adapter behind application services; all login/session responsibilities and any non-research market-data path remain separately gated. Fixture controls stay labelled until a later, separately approved research-universe integration consumes validated broker datasets.

This is research and analysis only, not personalized financial advice.
